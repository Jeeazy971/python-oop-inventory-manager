# 17.15 — Quand éviter la POO

## Principe

La POO est un outil parmi d'autres — pas une obligation.
Sur-utiliser les classes nuit à la lisibilité et à la maintenabilité.

## Cas où la POO est inutile

### 1 — Une seule opération, pas d'état
```python
# ✗ Classe inutile — aucun état, une seule méthode
class EmailValidator:
    def validate(self, email):
        return "@" in email

# ✓ Une fonction suffit
def validate_email(email):
    return "@" in email
```

### 2 — Grouper des fonctions utilitaires
```python
# ✗ Classe déguisée en module — pas d'état, pas d'instances
class MathUtils:
    def add(self, a, b): return a + b
    def multiply(self, a, b): return a * b

# ✓ Un module avec des fonctions
def add(a, b): return a + b
def multiply(a, b): return a * b
```

### 3 — Script one-shot
Un script qui tourne une fois (lire un CSV, générer un rapport)
n'a pas besoin de classes. Des fonctions enchaînées sont plus lisibles.

### 4 — Données sans comportement
Si tu groupes uniquement des données sans logique → dataclass ou dict.

## Règle de décision

| Situation | Quoi utiliser |
|---|---|
| État qui évolue + comportements | Classe |
| Plusieurs instances du même type | Classe |
| Transformation simple, pas d'état | Fonction |
| Données groupées sans logique | dataclass |
| Script ponctuel | Fonctions |
| Fonctions utilitaires sans lien | Module |

## À retenir

- Une classe sans état → c'est une fonction déguisée
- Une classe sans instances → c'est un module déguisé
- "Make it work, then make it clean" — commence simple, abstrait quand le besoin est confirmé
- Règle de 3 : si tu copies un bloc 3 fois → abstrait. Pas avant.
